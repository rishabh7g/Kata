A search that finds nothing

Someone types my car will not start into a help desk search box. The help desk holds exactly the right article. It is called Automobile engine fails to turn over in cold weather. The search comes back empty.

Nothing is broken. The search looked for the typed words inside the stored text, and the two sentences share no words. car is not automobile. start is not turn over. A search that compares words has no way to see that the two sentences are about the same thing.

What the reader wanted was a search that compares meaning. This Module is about the one move that makes that possible: turning a piece of text into numbers, so that "means something similar" becomes "sits close by".

An embedding is a list of numbers that stands for a text

Take the sentence "my car will not start". Hand it to a program and get this back:

[0.83, 0.12]

That list is an embedding: a fixed-length list of numbers made from a piece of text, arranged so that texts with similar meaning come back with similar numbers. The short word for a list of numbers like this is a vector — same thing, fewer syllables, and the word the tools use.

Two things to notice about it.

  • The words are gone. An embedding is not a squashed copy of the sentence, and you cannot read the sentence back out of it.
  • The length never changes. A three-word question and a three-page document both come back as lists of the same length. Real ones are long — 1536 numbers is a common size — but everything on this page works the same with two.

The numbers are coordinates

Two numbers make a point on a map: across, then up. Pretend, for this page only, that the first number means "how much this text is about vehicles" and the second means "how much it is about food". Real embeddings have no such tidy meaning per number, but the map picture holds, and the map picture is the point.

  • "my car will not start" → [3, 1]
  • "automobile engine fails to turn over" → [2, 1]
  • "banana bread recipe with walnuts" → [0, 4]

Draw those three points. The two car sentences land beside each other, over to the right. The recipe lands far away, up top. They landed there without sharing a single word, because the numbers came from meaning rather than spelling. That is the whole idea. Meaning became a position, so "related" became "nearby" — and everything after this is arithmetic.

Cosine similarity: do two arrows point the same way?

Draw an arrow from the corner of the map out to each point. Now the question "are these two texts about the same thing?" has become "do these two arrows point the same way?".

Cosine similarity is the number that answers it. It runs from 1 (the arrows point the same way) through 0 (they sit at a right angle, so the texts have nothing to do with each other) down to -1 (they point opposite ways). Three steps, worked here by hand.

  1. Multiply the matching numbers and add the results. That total is called the dot product.
  2. Measure each arrow's length: square its numbers, add them, take the square root.
  3. Divide the dot product by the two lengths multiplied together.

For [3, 1] and [2, 1] — the two car sentences:

  • dot product: (3 × 2) + (1 × 1) = 7
  • lengths: √(9 + 1) = √10 ≈ 3.16 and √(4 + 1) = √5 ≈ 2.24
  • 7 ÷ (3.16 × 2.24) ≈ 0.99

For [3, 1] and [0, 4] — a car sentence and the recipe:

  • dot product: (3 × 0) + (1 × 4) = 4
  • lengths: 3.16 and √(0 + 16) = 4
  • 4 ÷ (3.16 × 4) ≈ 0.32

0.99 against 0.32. Rank a pile of documents by that number and the nearest ones come out on top — which is a meaning-based search, built out of multiplying and adding.

Why the angle rather than the plain distance between the two points? A long document tends to produce a long arrow, so distance partly measures how much text there is. Direction does not care how much you wrote, and topic is what direction carries.

Where the numbers come from

Nobody writes embeddings by hand. You call an embedding model: a program that takes text in and gives a vector back. Trained means it was shown an enormous pile of text until texts that people use in similar ways came out with similar numbers. You do not train one. You call one, the way you call a weather service.

Two rules that bite beginners:

  • Every vector you compare has to come from the same model. Numbers from two different models are not comparable, in the way two people's private shorthand is not.
  • One model gives the same text the same vector every time, so you can work the vectors out once and store them.

In Python the usual way to call one is through LangChain, a library that puts many AI providers behind one shared set of calls. Its Embeddings piece has two methods worth knowing: embed_query(text) for the single text you are searching with, and embed_documents(texts) for the pile you are searching through. Which company's model actually runs is one line of setup; the code that does the comparing never mentions it.

What people build on top of this

Two things, named here and explained in their own Modules — come back for them whenever you want them, in any order:

  • Semantic search — the help desk case above. "Semantic" means meaning-based, as opposed to word-based: embed the question, embed the documents, return the nearest ones.
  • Retrieval-Augmented Generation — search your own documents first, then hand what you found to a chat model so its answer is grounded in them rather than made up.

The short version

  • An embedding is a fixed-length list of numbers made from a text by a trained model, and the text's words are not in it.
  • Similar meaning lands nearby. Cosine similarity says how nearby, from 1 (same direction) down through 0 (unrelated).
  • Word-matching search misses "car" against "automobile" because it compares spelling; embedding search finds it because it compares position.
  • Compare only vectors from one model, and store them, because the same text always comes back with the same numbers.

The right answer, buried in forty pages

The help desk from the Embeddings Module keeps one file: a handbook covering everything the company supports. Section one is car trouble. Section two is the canteen's banana bread. Section three is how to reset a password.

Someone types my car will not start. This search compares meaning rather than spelling, so it does find the handbook. What it hands back is the handbook — forty pages of it, with the two sentences that answer the question somewhere in the middle.

Nothing is broken. The handbook went into the search as one piece, so one piece is the smallest thing the search can return. This Module is about the work that has to happen before anyone asks anything, so that a search has something answer-sized to hand back.

Ingestion is four moves: load, split, embed, store

Ingestion is the work of turning files you already have into a pile of small searchable pieces. It is four moves in a row, and the rest of this page takes one section each.

  1. Load — read the file and turn it into text, plus a note of where the text came from.
  2. Split — cut that text into small pieces.
  3. Embed — turn each piece into a list of numbers.
  4. Store — keep those numbers somewhere they can be searched.

None of it happens while a reader waits. Ingestion runs ahead of time, once per file, and the last section on this page says what that buys.

Load: a file becomes a document with a label

A loader is library code that knows how to read one kind of source — a PDF, a web page, a folder of text files — and hands back the same shape whatever it read. That shape is a document: the text itself, plus metadata, which is a short set of labels saying where the text came from. source: handbook.pdf and page: 12 are metadata.

Loaders look like the dull stage, and they decide something that cannot be recovered later. The labels a loader attaches are the only way a search hit will ever be able to say which file and which page it came from. Throw them away here and no later stage can put them back.

Why the whole handbook does not work

Storing a forty-page file as one piece goes wrong twice over.

The first problem is size. Whatever reads the result afterwards — a person, or a chat model with a context limit, meaning a cap on how much text it can take in at once — has to wade through the whole file to reach two sentences.

The second problem is subtler, and it is worth working by hand. Pretend each text becomes two numbers: the first is how much it is about vehicles, the second how much it is about food. Real ones run to hundreds of numbers with no such tidy meaning, and two is enough here.

  • the car section → [2, 1]
  • the banana bread section → [0, 4]
  • the question "my car will not start" → [3, 1]

Embed the handbook as one text and what comes back points between its sections — near [2, 5], the two section arrows added together.

Cosine similarity is the number that says whether two of these arrows point the same way: 1 is the same direction, 0 is unrelated. It is the dot product — matching numbers multiplied and added — divided by the two arrow lengths multiplied together. The Embeddings Module works through why; the arithmetic is short enough to check here.

  • the question against the whole handbook: (3 × 2) + (1 × 5) = 11, lengths √10 ≈ 3.16 and √29 ≈ 5.39, so 11 ÷ (3.16 × 5.39) ≈ 0.65
  • the question against the car section alone: (3 × 2) + (1 × 1) = 7, lengths 3.16 and √5 ≈ 2.24, so 7 ÷ (3.16 × 2.24) ≈ 0.99

0.65 against 0.99. The car section never moved. Binding banana bread to it dragged the arrow up and away from the question, and that is the whole problem in one number: a document's vector is a blur of every topic inside it. The more a file covers, the blurrier it gets, and the less any one question points at it.

Split: chunk size and overlap

A chunk is one of the small pieces a text gets cut into, and chunking is the cutting. Two settings decide how it goes.

Chunk size is how much text goes in one chunk, counted in characters. Both directions cost something.

  • Small chunks have sharp meaning, because there is only one topic in each. A chunk too small stops holding a whole answer.
  • Big chunks keep more context around each sentence, and drift back towards the blur above.

Around 1000 characters is a common starting point, and it is a starting point rather than a rule — the right size depends on how the source is written.

Overlap is how much of the end of one chunk gets repeated at the start of the next. It exists because cuts land mid-thought. The two sentences that answer our question read:

"In cold weather the engine may fail to turn over. Hold the key down for ten seconds before releasing it."

Cut between them with no overlap and one chunk states a problem with no fix, while the next states a fix that never mentions cold weather or an engine. Neither chunk answers the question on its own, and the answer was in the file the whole time. Repeat the tail of each chunk at the head of the next and the thought survives the cut, whole, in one chunk.

Overlap is paid for in chunks. Chunk size minus overlap is the step — how far along the text each new chunk starts.

  • size 100, overlap 20, so step 100 − 20 = 80
  • a 300-character section gives chunks starting at 0, 80, 160 and 240 — four chunks
  • with no overlap the step is 100, the starts are 0, 100, 200, and the same section gives three

More overlap means more chunks, more vectors, more storage, and the same sentence coming back in two different hits. Overlap of a fifth of the chunk size or less is the usual compromise.

One more thing helps here: a splitter that cuts at natural boundaries. RecursiveCharacterTextSplitter tries paragraph breaks first, then line breaks, then sentence ends, and only falls back to cutting mid-word when a stretch of text offers it nothing better.

Embed: one vector per chunk

Each chunk now goes through an embedding model — a program that takes text in and gives back a fixed-length list of numbers, called a vector, arranged so that texts with similar meaning come back with similar numbers. That one sentence is all this page needs; the Embeddings Module is there when you want the rest.

Two habits carry over from it. Chunks and questions have to be embedded by the same model, because numbers from two different models are not comparable. And the same text always comes back with the same vector, which is why the vectors are worth working out once and keeping.

Libraries take the whole pile at once rather than one chunk at a time — embed_documents(texts) in LangChain — which is one network call instead of a hundred.

Store: a vector store holds three things per chunk

A vector store is a database built for one question: given this vector, which stored vectors point most nearly the same way? It answers that using an index, an arrangement of the data that makes lookup fast without comparing the asked-for vector against every row.

Each row holds three things, and each earns its place.

  • The vector — what actually gets compared. Nothing else in the row is searched.
  • The chunk's text — what gets handed back. A vector cannot be turned back into its text, so if the row does not keep the text, the text is gone.
  • The metadata — source, page, whatever the loader attached. A hit that cannot name its file cannot be checked by the person reading it.

Chroma, FAISS and pgvector are three of the common ones. Which you pick is a line of setup; the four moves on this page do not change.

Ingestion runs before question time

Everything above happens once per document, ahead of any question. When a question does arrive, the work is short: embed the question with the same model, ask the store for the nearest rows, and read what comes back. That is why the slow stages sit here rather than in the reader's wait.

  • Retrieval-Augmented Generation — hand those nearest chunks to a chat model so its answer is built out of your documents.
  • Agents & Tool Use — a model that decides for itself when to go searching.

The one maintenance job ingestion creates: when a file changes, its chunks have to be re-ingested. The store keeps answering with the old text until they are, and it has no way of knowing the file moved on.

The short version

  • Ingestion is load, split, embed, store — all of it before anyone asks a question, and again whenever a document changes.
  • A loader turns a file into a document: text plus metadata saying where the text came from. Labels dropped here cannot be recovered later.
  • A whole document embedded whole is a blur of every topic in it: 0.65 against the question, where its car section alone came out at 0.99.
  • Chunk size sets how sharp each piece is; overlap repeats the tail of one chunk at the head of the next so a thought cut in half survives.
  • A vector store row is a vector to search, the text to hand back, and metadata to prove where the text came from.

A confident answer that was never true

The help desk from the Embeddings and Ingestion Modules keeps one handbook, and now it has a chat model to answer with. Someone types my car will not start. The answer comes back straight away: check the battery terminals for corrosion, then call the fleet desk on extension 4400.

There is no extension 4400. There is no fleet desk. The handbook says to hold the key down for ten seconds in cold weather, and nobody ever showed the handbook to the model.

Nothing is broken. A chat model writes by predicting what words come next, and what it knows about is the pile of public text it was shown while it was being built. Your handbook was not in that pile. Asked about something it has no record of, the model does not go quiet — it writes the most plausible-looking sentence it can, and an extension number is exactly the sort of thing that follows a question about a company handbook.

Making it up has a name: hallucination

A hallucination is an answer a model states as fact with nothing behind it. It is not a bug and it is not lying. The model is doing the one thing it does, and there is no store of facts inside it to check the sentence against.

Two things make hallucinations hard to live with.

  • They read exactly like correct answers. Same tone, same confidence, same specific-sounding detail.
  • The model cannot flag them. It has no sense of which of its answers came from something it was shown and which it filled in.

You could retrain the model on your handbook. That is slow, costly, and out of date the day the handbook changes. This Module is the other way: leave the model alone and hand it the right text at question time.

Retrieve, then generate

Retrieval-Augmented Generation — RAG for short — is one step added in front of the model. Before the question goes anywhere near it, the question goes to your own documents first, and whatever comes back travels with it.

Four moves, in order.

  1. Embed the question — turn it into a list of numbers, called a vector, using the same model that embedded the documents.
  2. Retrieve — ask the store which stored chunks sit nearest that vector, and take the nearest k of them. A chunk is one small piece a document was cut into; k is however many you ask for.
  3. Build the prompt — the prompt is the whole message the model receives. Paste the fetched text into it, above the question. That pasted text is the context.
  4. Ask — send the prompt and tell the model to answer from the context.

The name is the description. An answer is generated by the model, and retrieval — fetching text you already have — is what it is augmented with. The model itself is untouched: it learned nothing, and it will not remember any of this next time.

One question, worked end to end

The Ingestion Module cut the handbook into chunks and put each one in a vector store, a database that answers one question: given this vector, which stored vectors point most nearly the same way? Two of those chunks are enough to work the whole thing by hand.

  • the car chunk — "In cold weather the engine may fail to turn over. Hold the key down for ten seconds before releasing it." → [2, 1]
  • the banana bread chunk → [0, 4]
  • the question "my car will not start" → [3, 1]

Real vectors run to hundreds of numbers with no tidy meaning each. Two is enough here: read the first as how much a text is about vehicles and the second as how much it is about food.

Cosine similarity is the number saying whether two of these arrows point the same way — 1 is the same direction, 0 is unrelated. It is the matching numbers multiplied and added, divided by the two arrow lengths multiplied together.

  • the question against the car chunk: (3 × 2) + (1 × 1) = 7, lengths √10 ≈ 3.16 and √5 ≈ 2.24, so 7 ÷ (3.16 × 2.24) ≈ 0.99
  • the question against the banana bread chunk: (3 × 0) + (1 × 4) = 4, lengths 3.16 and 4, so 4 ÷ (3.16 × 4) ≈ 0.32

0.99 against 0.32, so the car chunk is what k = 1 fetches. Now the prompt gets built, and it is three plain pieces of text stuck together:

  • an instruction — answer using only the context below, and if the context does not answer the question, say so
  • the context — the car chunk's text, word for word
  • the question — "my car will not start"

That whole thing goes to the model, which reads it and answers: in cold weather the engine may fail to turn over, so hold the key down for ten seconds. It is the same model that invented extension 4400. What changed is that the sentences it needed were sitting in front of it.

Grounding: answer from what is in the context

An answer is grounded when every claim in it traces back to text that was in the prompt. Grounding is what the fetched chunks buy, and two lines of instruction are what ask for it.

  • Answer using only the context below. Without this, the context reads as background rather than as the source, and the model is free to blend it with whatever else it holds.
  • If the context does not answer the question, say so. This is the more valuable of the two. It gives the model somewhere to go when the fetch came back with nothing useful, and "the handbook does not cover this" is a far better answer than a fluent invention.

Grounding is asked for rather than guaranteed. The model can still wander, which is the third failure below.

Citing the source

The chunks that come back carry their metadata — the labels the loader attached saying which file and which page the text was cut from. Print those beside the answer and the reader gets a citation: handbook, page 12.

That matters for a reason worth being blunt about. A grounded answer that cites nothing still has to be taken on trust, and it looks exactly like a hallucination. A citation turns "trust me" into "go and look", which is the only way anyone catches the times it went wrong.

What k trades off

k is how many chunks get fetched, and it is the one dial most worth understanding. The Ingestion Module cut chunks at around 1000 characters, so the arithmetic is short:

  • k = 1 — about 1000 characters of context
  • k = 4 — about 4000
  • k = 20 — about 20000

Small k is cheap and sharp, and it bets everything on the top chunk being right. If the answer spans two chunks, or the best chunk ranks second, a small k leaves the answer out of the prompt entirely.

Large k makes that miss unlikely and costs on three counts. Models charge by the token — a token is roughly a short word or a piece of one — so more context means more money and a longer wait. Models also have a context limit, a cap on how much text they can take in at once, and enough chunks will hit it. And the useful passage now sits among a crowd of near-misses, which is a harder read, not an easier one.

4 to 8 is a common starting point. Turn it up when answers come back missing things, down when they come back vague.

Three ways this goes wrong

Every RAG failure lands in one of three places, and from the outside they look the same — a wrong answer.

  • Retrieval miss — the chunk holding the answer was never fetched, so the model was asked to answer from text that does not contain it.
  • Context overflow — so much was fetched that it hit the context limit, or the passage that mattered got lost in the crowd.
  • Answering from memory — the right passage was in the prompt and the model answered from its training anyway.

Telling them apart takes one habit: print the fetched chunks next to the answer. If the passage is not there, it is a retrieval miss and the fix is in the fetching — different k, different chunking, a better question. If the passage is there and the answer disagrees with it, the fix is in the prompt.

A retriever is the fetching, packaged

Libraries wrap the fetch step in a retriever: an object with one job, taking a question and handing back documents. In LangChain, store.as_retriever(search_kwargs={"k": 4}) makes one from a vector store, and retriever.invoke(question) runs it.

The point of the wrapper is that the code around it stops caring where the documents came from. A retriever can be a vector store, a word-matching search, two of those combined, or something that fetches and then re-ranks. The four moves above do not change when you swap one for another.

The short version

  • A model asked about text it was never shown answers anyway, in the same confident voice it uses when it is right. That is a hallucination.
  • RAG is four moves: embed the question, retrieve the nearest k chunks, paste them into the prompt as context, ask the model to answer from them.
  • Nothing about the model changes. The fetched text arrives as ordinary words in one message and is gone by the next question.
  • Grounding is asked for in the instruction, and the second half of that instruction — say so when the context falls short — is what buys an honest "I do not know".
  • k trades a cheap, sharp fetch that can miss against a costly, noisy one that buries the answer. Small k misses; large k overflows; either way, print the chunks to see which failure you have.

The cost nobody could look up

The help desk from the earlier Modules retrieves before it answers now. Someone types my car will not start, and the depot is 27 miles away — what will the tow cost? The nearest handbook chunk comes back, and the first half of the reply is right: in cold weather the engine may fail to turn over, so hold the key down for ten seconds.

Then comes the second half. A 27 mile tow comes to about 88 pounds.

There is no 88 pounds. Today's tow rate is 4 pounds a mile, and it lives in the depot price list — a page that changes on Mondays and was never ingested. No chunk holds it, so retrieval could not have fetched it. The model was handed a question, some fetched text, and one shot at a reply, so it filled the gap with a plausible-looking number. It did the multiplication in its head as well: 27 × 4 is 108.

Two things were missing, and they are the same thing. The answer needed work nobody had built into the pipeline — read today's rate, then multiply — and the pipeline runs the same steps in the same order whatever it is asked.

A chain runs fixed steps; an agent picks the next one

That pipeline is a chain: steps you wrote down in an order, run top to bottom, every time. Embed the question, fetch four chunks, paste them into the prompt, ask. The model sits inside it as one step and decides nothing about the shape of the run.

An agent is the other arrangement. The model is handed a goal and a short list of things it is allowed to run, and each turn it picks one — or decides it has enough and answers. Your code is the part that runs whatever it picked.

The difference is one question: who decided the steps?

  • in a chain, you did, when you wrote the code
  • in an agent, the model does, one step at a time, while it runs

A tool is a function with a name and a description

A tool is an ordinary function in your code that the model is allowed to ask for. Nothing special about the function itself: rate_per_mile("tow") reads a price list and returns 4.0.

What makes it a tool is what the model is told about it. Three short pieces travel with the question, for each one:

  • the name — rate_per_mile
  • the description — one line saying what it does: today's depot rate in pounds per mile for a named service
  • the arguments — what it takes, and of what type: service, a string

That list is everything the model gets. It does not see the function body. It never runs anything itself. It has no record of what the function returned an hour ago. The description is the model's only manual, so a vague one is a tool that gets picked at the wrong moment — which is why that one line is where the effort goes.

One question, worked one turn at a time

Three tools, and the question from the top of the page.

  • search_handbook(query) — the handbook passage nearest a question
  • rate_per_mile(service) — today's depot rate, in pounds per mile
  • multiply(a, b) — two numbers multiplied

The model starts with the goal and nothing else. Read down the turns.

  1. It picks search_handbook("car will not start"). Your code runs it: the question embeds to [3, 1], the car chunk at [2, 1] comes out at about 0.99 against it where the banana bread chunk at [0, 4] is 0.32, so the car chunk comes back — hold the key down for ten seconds.
  2. That text goes back to the model under the goal, as the result of turn 1. Now it picks rate_per_mile("tow"). Your code runs it and hands back 4.0.
  3. Both results are in front of it. It picks multiply(27, 4). Your code hands back 108.
  4. The goal and all three results go back one more time. This turn the model picks no tool. It writes the answer: hold the key down for ten seconds in cold weather, and a 27 mile tow comes to 108 pounds.

Four turns, three tool calls. None of that order was fixed when the code was written. The model searched first because the question opened with a fault, and it could not multiply before the rate came back.

Two details are what make the loop work at all.

  • Every turn re-sends everything. The model remembers nothing between calls. Turn 3 works because the goal and the first two results are all in the message again, in full.
  • Your code runs the tools. What comes back from the model is a name and some arguments — text. Whether that call is allowed, and what it does, stays yours to decide.

The loop has a name: ReAct

Take the example away and four moves are left, going round:

  1. the model reads the goal and everything that has happened so far
  2. it picks a tool and its arguments, or decides it is done
  3. your code runs that tool and takes the result
  4. the result is added to the history, and it goes round again

The run ends when move 2 comes back with an answer instead of a call.

This is the ReAct pattern — reason about what is known, act by calling one tool, then reason again on what came back. The name is worth knowing because most agent libraries are this loop with comfort built around it.

Guardrails: a loop that can fail to stop

Move 2 is a model deciding it is done, and a model can fail to decide that. The usual shape is dull: the same call with the same arguments, turn after turn, each one paid for. Nothing inside the loop ends that — the tool answers every time it is asked.

Max steps is the stop from outside: how many tool calls a run may make before your code ends it. Against the four-turn run above:

  • max_steps = 2 — ends after rate_per_mile, before the multiply, so the run finishes with no answer. Saying that is the honest reply
  • max_steps = 5 — the run above finishes, with two spare
  • max_steps = 25 — a run that has gone wrong repeats its wrong call twenty-five times before anything stops it

Cost climbs faster than the step count, because of the re-sending above. Five steps is up to six model calls, and each one carries more text than the one before it.

Two more limits sit next to it.

  • A retry budget — how many times one failing tool call is tried again before the run gives up. 2 is a normal number; a tool that failed twice is usually going to keep failing
  • What the model may not do — the tool list is the whole surface it can reach, so a tool that deletes, pays, or emails is a decision rather than a convenience. The common rule: tools that read run on their own, tools that change something wait for a person

When not to use an agent

If you already know the steps and the order they go in, write them down. That is a chain, and it wins on all three of the things that matter:

  • Cost — a chain makes one model call. The run above made four, each carrying more text than the last
  • Speed — one round trip against four, one after another
  • Predictability — a chain does the same thing today and next Tuesday. An agent's route is chosen while it runs, so the same question twice can take two different paths

Retrieval is the example. Every question wants the same three moves in the same order — embed, fetch, ask — so there is nothing there for a model to decide, and handing it the decision buys variability at four times the price.

Reach for an agent when the next step genuinely depends on what the last one returned, or when a question could need any of several tools and you cannot tell which one in advance. That is the case the loop pays for.

Three ways this goes wrong

From the outside these look alike — a wrong answer, or no answer.

  • Wrong tool — the model picked a tool that cannot answer the question, usually because two descriptions overlap or one of them is vague.
  • Bad arguments — the right tool, called with input it cannot use: rate_per_mile("towing") when the price list is keyed on "tow".
  • Runaway loop — the model never decides it is done, so one call repeats until max steps ends the run.

Telling them apart takes one habit: print each turn's tool name and arguments beside the result that came back. Wrong name, and the descriptions are what need work. Right name with arguments the tool rejected, and the fix is in the argument description or in what the tool says when it fails. The same call over and over, and it is the loop — cap it, then look at whether any result ever told the model something it did not already have.

The loop, packaged

Libraries ship the loop so that you write the tools and not the plumbing. In LangChain the @tool decorator turns a function into a tool: the name comes from the function name, the description from its docstring, the arguments from its type hints — which is one more reason that docstring is worth writing carefully. model.bind_tools([...]) hands the list to the model, and an agent executor is an object that runs the four moves round and round, taking max_iterations as its max steps.

What the wrapper buys is that the loop stays the same whatever the tools are. What it hides is every individual turn, which is exactly what you want to see when an answer comes out wrong — hence the printing habit above, and the second Module named below.

What this leaves for later

Two Modules of their own, named here and needed by nothing on this page.

  • LangGraph — the loop drawn out as nodes and edges with state you can see, for when one model deciding everything is too loose.
  • LangSmith — every turn of a real run recorded and searchable, rather than printed and lost.

The short version

  • A chain runs steps you fixed in advance. An agent hands the model a goal and a list of tools, and the model picks the next step each turn.
  • A tool is a plain function. All the model sees is its name, its one-line description and its arguments, so the description is the whole of what it chooses on.
  • The loop is four moves repeated — read the goal and history, pick a tool or stop, run it, add the result. That is the ReAct pattern.
  • Every turn re-sends the whole history, so cost climbs faster than the step count, and max steps is what ends a run that will not end itself.
  • If you know the steps and their order, write a chain: cheaper, faster, the same every time. Keep the agent for when the next step depends on what came back.

The step nobody was asked about

The help desk from the earlier Modules answers the tow question now. Someone types my car will not start, and the depot is 27 miles away — what will the tow cost? and the run makes three calls out to your code: the handbook passage comes back, today's rate comes back as 4 pounds a mile, and 27 × 4 comes back as 108. The reply is right. Hold the key down for ten seconds in cold weather, and a 27 mile tow comes to 108 pounds.

Then the depot asks for one more thing the help desk can do. book_tow(miles) sends a truck. It charges the customer, and it cannot be taken back.

The next run books a tow. Nobody was asked first.

Look at where you would put the asking. The code that runs the whole thing is one line: runner.invoke(...). The turns, the choice of what to call each turn, the history carried between them — all of it happens inside that call. You have two places to stand, before it and after it, and the thing you need to stop is in the middle.

Four things are wanted here, and they are the same thing four times over.

  • stop the run before one named step
  • read what the run has worked out so far
  • let a person say yes or no
  • carry on from that point, rather than starting the run again

Every one of them needs the middle of the run to be something you can name and something you can save.

A graph is nodes for the work and edges for what runs next

LangGraph is a library for writing that middle down. Three words carry it.

  • A node is a function that does one piece of the work. It is given the run's shared state, and it returns the part of that state it changed.
  • An edge says what runs next: when retrieve finishes, run look_up_rate.
  • A graph is a set of nodes and the edges between them, declared before anything runs.

Those last four words are the difference. In the agent from the previous Module the route was decided while running, inside the executor, and nothing wrote it down. Here the possible routes are named first, in your code, and what happens at run time is that one of the named ones is taken.

Declared first does not mean fixed. A graph can still hand the choice to the model — that is the conditional edge further down. It means the choices have names, and a name is something you can stop at, print, and save.

State: one object every node reads and writes

Without a shared object, a step has to be handed whatever the step before it produced. The fetched passage goes to the pricing step so the miles can be read out of it; the rate goes to the pricing step too; the total goes to the step that writes the reply, along with the passage again. Five values in a line of four functions means most of them are passed through functions that never look at them, and a sixth value means editing every signature in the line.

State is the other arrangement: one object, its keys declared once, that every node is given. A node reads whatever keys it needs and returns only the keys it changed. The graph merges that return value into the state and hands the result to the next node.

The tow run's state holds four keys.

  • question — what the person typed
  • chunk — the handbook passage that came back
  • rate — pounds per mile, today
  • cost — the total for the tow

Declaring it as a typed object — the key names and what type each one holds, written down — is what makes a wrong key a mistake your editor points at rather than a None that turns up three nodes later. A fifth value is a fifth key: one line added, and no signature anywhere changes.

One question, run through the graph

Four nodes, wired in a line, on the question from the top of the page. Read down and watch the state fill up.

  1. retrieve reads question. The question embeds to [3, 1]; the car chunk at [2, 1] comes out at about 0.99 against it, where the banana bread chunk at [0, 4] is 0.32. It returns chunk — hold the key down for ten seconds. State: two keys.
  2. look_up_rate reads the service out of question and the price list off disk. It returns rate as 4. State: three keys.
  3. price reads rate and the 27 miles. It returns cost as 108. State: four keys.
  4. write_answer reads chunk and cost and returns the reply.

Every node was handed the whole state and gave back one key. Nothing was passed hand to hand, and write_answer read the passage that retrieve found without any node in between having to carry it.

Conditional edges: the routing, now visible

A conditional edge is an edge whose next node is decided while the run happens. It is a function: it reads the state and returns the name of the node to run next.

The agent's own loop is the shortest example. One node calls the model, one node runs whatever tool the model asked for, and the edge between them reads the last message.

  • the model asked for a tool — go to the tools node
  • the model wrote an answer instead — go to the end

Add an edge from tools back to the model node and that is the loop from the previous Module, drawn: two nodes, one conditional edge, one edge back. What was a while inside a library object is now four lines you can read.

The step cap comes with it. Keep a steps count as another key in the state, add it to what the routing function reads, and the dial lives in the same place as every other routing decision:

  • steps >= 2 — the run ends after the rate comes back and before the multiply, so it finishes with no total. Saying that is the honest reply
  • steps >= 5 — the three-call run from the previous Module finishes, with two spare
  • steps >= 25 — a run that has gone wrong repeats its wrong call twenty-five times before anything stops it

Same three numbers as the executor's max_iterations, in a function you wrote rather than an argument you handed over.

Persistence: a state you can save is a run you can pause

A checkpointer is somewhere for the graph to save the state after every node, filed under a thread id — a name for one run. Give it memory while you are trying things out, or a database once it matters, and every step of every run leaves a saved copy behind.

Saving after each node buys three things.

  • Resume. Invoke the graph with the same thread id and no new input. It reads the last saved state and carries on from where it stopped.
  • Recovery. A run that dies at node three starts again at node three, not at the top, so the two model calls before it are not paid for twice.
  • Hindsight. The state as it stood after each node is still there to read, which is what the failures section below leans on.

Resume is the one to hold on to. A run that can be picked up is a run that can be put down.

Stopping before the risky step

Name a node as one to stop before, and the graph runs up to it and returns. The state is saved. Nothing has been booked.

Now a person reads what the run has: the passage, the rate, the total. Then one of three things happens.

  • they approve — resume the run, and book_tow is the next node to go
  • they change something — write a corrected key into the saved state first, then resume
  • they refuse — end the run there. The truck was never sent

That is human in the loop: a run that pauses for a person and carries on afterwards. The previous Module ended on a rule of thumb — tools that read run on their own, tools that change something wait for a person — which was yours to keep by hand. Here it is a list of node names, given to the graph when you build it.

When a chain or a single agent is still enough

A graph is more to write than either: a state type, a function per node, the edges, and something to save state with. Three cases do not pay for it.

  • Fixed known steps. Retrieve, paste, ask, the same three every time. That is a chain, and wiring it as a graph adds names to steps nobody needs to stop at.
  • One model, read-only tools. If nothing the tools do can be regretted and no run is long enough to want resuming, the agent executor from the previous Module already runs the loop for you.
  • A run that finishes in seconds. Persistence earns its place when runs are long, or paused, or expensive to repeat.

Reach for a graph when a step needs a person's yes, when a run is long enough that you will want to pick it up again, or when there are several named steps and you want to read the route between them rather than infer it.

Three ways this goes wrong

From the outside these look the same — a wrong answer, or a run that never gets to one.

  • Dropped update — a node does its work and returns nothing, or returns a key the state never declared, so the merge puts nothing in. The next node reads what was there before: a cost worked out from a rate that never landed.
  • Wrong branch — the routing function reads a key that nothing has written yet, so an empty value sends every run down the same edge.
  • Cycle that never ends — an edge loops back to an earlier node under a condition that never comes true, so the graph goes round until a step cap outside it stops the run.

Telling them apart takes one habit: print the state after every node — the node's name, and the keys that changed. A node whose line changed no keys is a dropped update. A branch taken with the key it read still empty is a wrong branch. The same node's name over and over with the same keys is the cycle, and the fix is the condition on the edge, not the node.

What this leaves for later

Named here, and needed by nothing above.

  • LangSmith — every node of every real run recorded with the state it produced, kept and searchable, rather than printed to a terminal and lost when the window closes. The printing habit above is the hand-rolled version of it.
  • Graphs inside graphs — a node that is itself a whole graph, which is how one finished agent becomes a single step in a larger one.
  • Self-Correcting RAG — a graph whose edges point backwards on purpose: an answer that fails a check goes back to the node that wrote it, and what ends the cycle is the check passing.

The short version

  • A graph is nodes and edges written down before the run: a node is a function that does one piece of work, an edge says what runs next.
  • State is one typed object every node reads and returns changes to, so values stop being threaded through functions that do not use them.
  • A conditional edge reads the state and returns the name of the next node — the routing an agent does anyway, in a function you can read.
  • A checkpointer saves the state after every node under a thread id, so a run can be paused, resumed, and picked up after a crash.
  • Saved state is what makes human in the loop possible: stop before the step that spends money, let a person look, then carry on from there.

A wrong answer, and nowhere to look

The help desk from the earlier Modules has grown. Someone types a tow, 27 miles — what will it cost? and the reply comes back: 54 pounds.

It should be 108. The depot charges 4 pounds a mile for a tow, and 27 × 4 = 108. Something in that run used 2.

Now go and find it. One question went in and one sentence came out, and in between the help desk made six calls of its own that nobody saw: a model call deciding what to do first, a fetch against the handbook, a price lookup, a multiply, another model call, and a last one that wrote the sentence. Any of the six could be the one that went wrong.

The two Modules before this one both ended on the same suggestion. Print each turn's tool name and arguments beside the result. Print the state after every node, the name beside the keys that changed. Both work, and both have the same three holes in them.

  • They show what you thought to print. The prompt actually sent — the whole message the model receives — what it cost, and how long it took are in no print unless you went back and added one.
  • They are gone when the terminal window closes. The run a colleague saw yesterday cannot be looked at today.
  • They are yours alone. A run that went wrong on somebody else's machine left no record at all.

A trace is the recorded tree of one run

A trace is the record of every call one run made, kept as a tree. One question in, one trace out.

Each call in that tree is a span: one piece of work, with four things written down.

  • what went in — the prompt, the arguments, the question
  • what came out — the reply, the returned value, or the error
  • how long it took
  • how many tokens it spent, for the calls that spend them. A token is roughly a short word or a piece of one, and it is what a model charges by

A tree rather than a list, because calls happen inside calls. The whole run is the root. A model call sits under it, and the tool that model asked for sits under the model call. Reading down the tree reads the run in the order it happened, and a span's children are everything it set off.

LangSmith is a hosted place to send traces to. Set its environment variables and the LangChain and LangGraph calls you already wrote start recording themselves. A @traceable decorator covers the rest, which is how a plain Python function of your own turns up in the tree beside them.

Reading a trace to find the failing step

Here is the trace of the 54 pound run. The root took 2.12 seconds and spent 1840 tokens, and it has five children.

  1. retrieve — in: the question. Out: the car chunk. A chunk is one small piece a document was cut into. The question as numbers is [3, 1], the car chunk at [2, 1] matches it at about 0.99, and the banana bread chunk at [0, 4] comes out at 0.32.
  2. model — out: call rate_per_mile(service="jump start").
  3. rate_per_mile — in: "jump start". Out: 2.
  4. multiply — in: 27 and 2. Out: 54.
  5. model — out: "a 27 mile tow is 54 pounds".

Read down and ask one thing of every span: was its input right, and was its output right for that input?

  • Span 1 fetched the car chunk at 0.99 over 0.32. Right input, right output. The retrieval is not it.
  • Span 2 was handed a question about a tow and asked for the jump start rate. Right input, wrong output. That is the failing step.
  • Spans 3, 4 and 5 each did exactly what they were asked. 2 really is the jump start rate. 27 × 2 really is 54. The sentence really does report the number it was given.

The rule is worth keeping. The first span whose output is wrong while its input was right is the one to fix. Everything after it is a faithful answer to a bad input, and rewriting any of it is work spent in the wrong place.

Three repairs sit behind that first bad span, and the trace says which one you need.

  • A bad retrieval — the passage in the span is not the passage that holds the answer.
  • A bad tool pick — the passage was right, and the tool the model chose, or the arguments it wrote, were not.
  • A bad final prompt — every span above is right and the last model call still wrote something none of them support.

Here it is the middle one. rate_per_mile takes a service name and the model wrote the wrong service, so the repair is in what the tool's description says a service name is.

One run tells you about one run

Rewrite the description, ask the tow question again, read 108, and you are finished — with that question.

You are not finished with the others. A jump start really does cost 2 a mile, and a description reworded to push the model towards a tow can push it there for every question. Banana bread was answered honestly yesterday, with the handbook does not cover this. Is it still? Nobody looked.

Checking by hand fails for a plain reason. It spends your attention per question, and attention is the thing that runs out. Four questions is a slow morning. Forty is never going to happen, so it stops happening at all, and changes go out unchecked.

A dataset is the questions, written down once

Evaluating is running a fixed set of questions against the app and judging the answers, every time something changes.

A dataset is that fixed set: pairs of an input and what a good answer contains.

  • "a tow, 27 miles, what will it cost" → 108
  • "a jump start, 27 miles, what will it cost" → 54
  • "my car will not start" → hold the key down for ten seconds
  • "how do I make banana bread" → the handbook does not cover this

How many rows is the dial worth understanding.

  • 4 — one per thing the help desk does. Enough to catch the repair that fixed the tow and broke the jump start, and silent about every question nobody wrote down
  • 40 — every failure of the last few months, a row each. A run takes a few minutes and costs about what a few minutes of model calls costs
  • 400 — a run is slow enough and dear enough that you stop doing it on every change, which is the point where a dataset stops working

Where the rows come from is the failures. Every run that came back wrong becomes a row, with what it should have said. The dataset grows out of the bugs, which is why it stays about the things that actually break.

Judges: exact where you can, written down where you cannot

A judge is whatever turns one answer into a verdict. There are two kinds, and the first is the better one whenever it is available.

Exact checks are ordinary code. Is 108 in the answer? Did it name the handbook page it used? Is it under a hundred words? These cost nothing, say the same thing every time, and need no checking themselves. Write the dataset so that as many rows as possible can be judged this way — a number in the expected answer is worth more than an elegant sentence.

An LLM as judge is a second model call. Hand it the answer, the question, the passage that was fetched, and a criterion — the standard, written out — and ask for a yes or a no. This is for what code cannot see. Does every claim in the answer appear in the passage? Does it answer the question that was asked? Does it say the handbook does not cover this, rather than inventing a recipe?

Write the criterion down in one place and leave it there. A criterion reworded between runs makes every comparison two changes at once, and you cannot tell which of them moved the result.

And be blunt about what a judge is. It is a model call. It carries every failure the app carries: it can be confidently wrong, it can wander, it can be talked round by a fluent answer. A judge reporting 3 out of 4 is not a measurement. It is a second opinion.

Two habits keep it honest.

  • Decide some yourself. Take ten answers, say yes or no by hand, and see how often the judge agreed with you. How often it did not is what its verdicts are worth.
  • Keep the exact checks. They are the part of the result that cannot argue with you.

Three ways this goes wrong

From the outside these look the same — a number that moves, or does not, with nothing to do about it.

  • Untraced step — a call made somewhere the tracing does not reach, so the tree has a hole exactly where the failing span should be.
  • Overfitted dataset — every row is a variation of the last thing that broke, so the count climbs and the app does not get better.
  • Trusted judge — the criterion is vague, so the judge's verdicts move from run to run, and a change that made things worse reads as an improvement.

Telling them apart takes one action: take the row that came out worst, open its trace, and read the tree beside the judge's verdict. A value in the tree with no span that produced it is the untraced step. A tree and a verdict that agree with each other, on a question nobody was complaining about, is the overfitted dataset — the failure you are chasing has no row. A tree holding an answer you would have passed against a verdict that fails it is the judge, and the repair is the criterion rather than the app.

The habit

Two moves, at two different moments.

  • Trace while building. Turn it on for the first run and leave it on. It costs a few environment variables, and the alternative is guessing at six calls you cannot see.
  • Evaluate before shipping a change. Not because the count is the truth, but because a change that fixes one question and quietly breaks two others looks exactly like a change that worked.

Neither belongs at the end. A trace switched on after the bad run is a trace of a different run.

  • Graphs inside graphs. The LangGraph Module named this and stopped. A node can be a whole graph, which is how one finished agent becomes a single step inside a larger one. Build the smallest version: take the help desk and drop it in as one step of something bigger. The traces nest the way the graphs do.
  • Running it for other people. Everything here ran from one machine, one question at a time. Serving it to a depot means a queue, retries, and a bill — and every number that bill is made of is already sitting in your traces.
  • The evaluation you have not written yet. Take the four rows above, add the last ten things that went wrong, and run them. Forty rows and two judges is a weekend of work, and it is the difference between changing this thing and improving it.

The short version

The reply the code could not read

The help desk from the earlier Modules fetches a handbook chunk before it answers. Someone adds one small step in front of the answering: ask the model whether the fetched chunk is actually about the question, and skip it if not. The instruction is short. Is this passage relevant to the question? Answer yes or no.

The model replies: Yes, the passage is relevant, because it describes what to do when the engine will not turn over in cold weather.

The code that reads that reply says if reply == "yes". That is false. The chunk is dropped, the model is asked to answer from nothing, and out comes an extension number that does not exist.

So the check becomes reply.lower().startswith("yes"). It works until the day the model opens with Certainly. Yes, and the chunk is dropped again. Then someone asks about banana bread, the model writes No, this passage is about cars — though yes, it is from the handbook, and the word being searched for is in there twice.

Nothing about the model is wrong. It was asked a question in words and answered in words. The problem is on the other side: a program was trying to find a value inside a sentence, and sentences do not hold values in any fixed place.

Prose is for people; code needs a shape

Structured output is asking the model to answer by filling in a shape rather than by writing a sentence. You describe the shape first — which fields it has, what type each one is, what each one means — and the model's reply arrives as an object with those fields filled.

The difference is where the reading happens.

  • With prose, the model writes freely and your code reads the sentence afterwards, guessing where the value is.
  • With a shape, the model does the reading. It has the passage and the question in front of it, works out the answer, and puts the answer in the one field the shape has for it. Your code reads a field.

Underneath, the same mechanism as the Agents & Tool Use Module: the shape is sent along with the prompt the way a tool's description is, and the model replies in the fixed notation called JSON, which the library turns into an object before your code sees it. None of that needs remembering. What matters is that a field called relevant of type bool is either True or False, and there is no third thing it can be.

Declaring the shape

In Python the shape is a class. Each field has three parts.

  • a name — relevant
  • a type — bool
  • a description — one line saying what goes in it: whether the passage answers the question

The description is the important one. It is the only instruction the model gets about that field, so it is the prompt for that field. Change it and the answers change, the way rewording a tool's description changes which tool gets picked.

Given the class, model.with_structured_output(Shape) hands back a model that answers in that shape. Ask it the same relevance question and the reply is not a sentence. It is an object, and reply.relevant is True or False, whatever words the model would have chosen.

Three shapes worth knowing

Most structured output is one of three shapes. The help desk uses all three.

  1. A yes or no. One field, bool. Is this chunk about the question. Does every claim in the answer appear in the chunks. The code reads reply.relevant and branches on it, and there is nothing to parse.
  2. A choice from a fixed list. One field whose type is the list of allowed values: the handbook, or the web. Written as Literal["handbook", "web"], it means the model must pick one of exactly those two strings, and cannot reply with a third. A choice like this is what sends a question one way or the other before any fetching happens.
  3. A record. Several fields together: the answer as text, the page numbers it relied on as a list of integers, and whether the handbook covered the question at all as a bool. One model call fills the whole record.

Each is the same move. Decide what your code needs to read, name it, type it, describe it, and let the model fill it.

The honest "I do not know", now a value

The Retrieval-Augmented Generation Module ended on two lines of instruction, and the more valuable one was: if the context does not answer the question, say so. That bought an honest reply. It did not buy anything the code could act on, because "say so" comes out as words — "the handbook does not cover this", or "nothing here mentions banana bread", or "I could not find that" — and the code is back to searching sentences.

Make it a field. covered: bool, described as whether the passages actually answer the question. The model still writes its honest reply in the answer field. It also sets covered to False, and now the code can do something about it: go to the web, tell the reader plainly, or ask a person. The instruction did not change. What changed is that its outcome has a place to land that a program can read.

The page numbers work the same way. Every chunk arrived carrying its metadata — the file and page it was cut from, attached at ingestion. Label each chunk with its page in the prompt, give the record a field pages: list[int], and the citation from the Retrieval-Augmented Generation Module stops being a phrase to spot at the end of a sentence and becomes a list the screen can print.

A string that says "yes" is not a yes

One small trap, worth its own heading because it is so common. A field can be declared as a string and described as 'yes' or 'no'. That is a shape, and the model will fill it. But the code that reads it still has to do two things before it can branch: lowercase the value, then compare it to the word. Two steps is two places to be wrong, and the day the model writes Yes. with a full stop the comparison fails silently.

Declare the field as bool and both steps disappear. There is nothing to lowercase and nothing to compare. The field is the branch.

The general rule is the one the Error Design Module puts at the centre: choose the shape so the mistake cannot be made, rather than checking for it afterwards. A type that has only two values cannot hold a third.

What a shape does not buy

A shape makes the reply readable. It does not make it true.

  • The model can fill pages with [12] when the passage it used was labelled page 14. The field is an integer list, exactly as declared, and wrong.
  • A choice from a fixed list is forced. Offer handbook or web and ask about banana bread, and the model picks one, because the shape has no room for neither. If neither is ever a real answer, give the list a third value, or make sure the one it falls back to is the one that costs least when it is wrong.
  • A field with a vague description gets filled with whatever the model takes it to mean. relevant, described as nothing more than "relevant", comes back True for any chunk from the same handbook.

And the model has to be able to do this at all. Structured output rides on the same ability as tool calling, and a model that cannot emit a tool call quietly gives back prose, or nothing. One test call on a question with a known answer, before anything else is built, is how you find out.

Three ways this goes wrong

From the outside all three look the same: the code branched, and the branch was wrong.

  • Right shape, wrong content — the fields are all the declared types and one of them is untrue. Nothing about a type catches this.
  • Forced choice — the shape offered two options and the question fit neither, so the model picked the nearer one and the code trusted it.
  • Vague field — the description left room, and the model filled the room with a meaning you did not intend.

Telling them apart takes one habit: print the filled shape beside the raw text it was filled from. A page number that is not in the labelled passages is the first. A choice that no reader would have made from the question is the second. A field that is technically defensible and practically useless is the third, and the fix is the description.

What this leaves for later

Named here, and needed by nothing above.

  • Self-Correcting RAG — a graph in which every decision is one of these shapes: a yes or no on each fetched chunk, a yes or no on the answer, a choice at the entry. Structured output is what makes the decisions readable enough to wire edges to.
  • LangSmith — the filled shape appears in the trace beside the prompt that filled it, which is the printing habit above, kept.

The short version

  • A program cannot reliably find a value inside a sentence. Structured output moves the reading to the model: describe a shape, and the reply arrives with the fields filled.
  • A field is a name, a type, and a description, and the description is the prompt for that field.
  • Three shapes cover most uses: a bool, a choice from a fixed list, and a record of several fields.
  • The honest "the handbook does not cover this" becomes covered: False, a value the code can branch on, and citations become pages: list[int].
  • Declare a yes or no as bool, never as a string that says "yes". A shape makes the reply readable, not true, so print the filled shape beside what it was filled from.

The habit nobody was there to keep

The help desk from the earlier Modules fetches a handbook chunk, pastes it above the question, and answers from it. Someone types what does the depot charge for a tow on a Sunday? The nearest chunk is the one about Sunday opening hours. It says nothing about charges. The reply comes back anyway: Sunday tows are charged at double the weekday rate.

There is no double rate. The handbook does not mention one. The fetch brought back the nearest chunk, which was about the wrong thing, and the model filled the gap the way the Retrieval-Augmented Generation Module warned it would.

That Module ended on a habit: print the fetched chunks beside the answer, and read them. Is the passage there? Does the answer agree with it? The habit works. It also needs a person sitting at the terminal, and the help desk answers two hundred questions a day with nobody reading a single chunk.

This Module makes the program keep the habit. Every check a person would make by eye becomes a small model call with a yes or no answer, and the graph from the LangGraph Module takes a different edge depending on the answer.

A judge is one model call with one yes-or-no question

A judge is a model call that is given two things and asked one question about them, and that answers by filling a shape with a single bool — the Structured Output Module's smallest shape. It is not the model that writes the answer. It is a second, separate call, with its own short instruction, whose only job is to look.

The Retrieval-Augmented Generation Module named three ways a RAG answer goes wrong. Each one gets a judge.

  • Retrieval miss — the chunk that came back is not about the question. The relevance judge is given one chunk and the question and asked: does this passage help answer it?
  • Answering from memory — the answer says things the chunks do not. The grounding judge is given the chunks and the answer and asked: does every claim in the answer appear in the passages?
  • A grounded answer that misses the point — every sentence traces back to a chunk, and none of them answers what was asked. The usefulness judge is given the question and the answer and asked: does this answer address the question?

Three failures, three judges, one question each. What the person at the terminal did by reading, a judge does by being asked.

The route, with the judges wired in

The LangGraph Module built a graph: nodes for the work, edges for what runs next, one shared state every node reads and writes. Here the state holds four keys.

  • question — what was typed
  • documents — the chunks in hand, which changes as the run goes
  • web_search — whether the fetch fell short and the web is needed
  • generation — the answer, once there is one

Five nodes carry the work, and the judges sit on the edges between them.

  1. Route. Before anything is fetched, one Structured Output choice decides where the run starts: a question on the handbook's own topics goes to retrieval, anything else goes straight to the web. A graph whose first node is chosen at run time has a conditional entry point, and this is one.
  2. Retrieve. The nearest k chunks, as before.
  3. Judge documents. The relevance judge runs once per chunk. The chunks it says yes to stay in documents; the ones it says no to are dropped. If any were dropped, web_search is set to true.
  4. Web search. Runs only when the flag is set. The search results come back as one more document and join the ones that survived.
  5. Generate. The answer, from whatever documents now holds.

Then the answer is judged twice, and the edge out of generate has three places to go.

  • grounded and useful — the run ends, and this is the answer
  • not grounded — back to generate, to try again from the same chunks
  • grounded but not useful — out to web search, because the chunks in hand were not enough

Those last two are edges that point backwards. The LangGraph Module called a cycle that never ends one of the three ways a graph goes wrong. These are cycles on purpose, and what ends them is a judge saying yes.

One question, run through the graph

The Sunday tow question, read down the nodes. Watch documents change.

  1. Route reads the question. Tows and charges are handbook topics, so it says retrieval.
  2. Retrieve fetches k = 4. The Sunday opening hours chunk is nearest. Behind it come a chunk on the weekday tow rate, one on the jump start rate, and one on banana bread.
  3. Judge documents asks the relevance judge four times. Opening hours: no. Weekday tow rate: yes. Jump start rate: no. Banana bread: no. documents shrinks from four to one, and web_search is set, because three were dropped.
  4. Web search runs the question against the web and adds the result as a fifth document, so documents is back to two.
  5. Generate answers from the tow rate chunk and the web result: the handbook gives 4 pounds a mile on weekdays and says nothing about Sundays, so a Sunday tow may be quoted on the day.
  6. The grounding judge reads the two documents and the answer. Every claim is in them. Yes.
  7. The usefulness judge reads the question and the answer. The answer says what the handbook knows and what it does not. Yes.

The run ends. Nothing on the way invented a double rate, because the opening hours chunk that would have prompted it was dropped at step 3, and the answer that came out was read twice before it left.

Count the model calls. The chain from the Retrieval-Augmented Generation Module made one. This run made the route, four relevance judgements, one generation, and two judgements on it: eight. That is the cost, and it is paid on every question.

The web is a fallback, not a second truth

The web search node adds its result to documents the same way a handbook chunk sits there. Nothing downstream treats it differently. The grounding judge reads it as a passage, and the answer that draws on it is grounded in it. That is right and it is also the thing to keep an eye on. A grounded answer is one whose claims trace back to what was in the prompt, and the prompt now holds text nobody at the depot wrote.

Two habits keep this honest. Label each document with where it came from — the handbook and page, or the web — so the citation says which. And treat the flag as information: a run in which web_search was set is a run in which the handbook fell short, which is worth counting even when the answer came out fine.

What ends a cycle

Two edges point backwards, and each one ends when a judge says yes. Nothing in the graph above says what happens if it never does. A grounding judge that keeps saying no sends the run back to generate, which produces another answer from the same chunks, which the judge reads again. The LangGraph Module's answer applies unchanged: keep a count in the state, read it on the same edge, and end the run with an honest reply once the count is spent. Two retries is a reasonable number. An answer the judge has refused twice is not going to be rescued by a third.

The library has a backstop of its own — a run that takes more than a set number of steps is stopped with an error — and it is a backstop, not a design. A run that hits it has no answer at all. A run that hits your own count has the honest one.

When the plain chain is still enough

Eight calls where there was one is not free, in money or in waiting. Three cases do not pay for it.

  • The corpus always covers the question. If every question is on the handbook's own topics, the route always says retrieval and the relevance judge rarely says no. Pay for a judge that never disagrees and you have bought nothing.
  • A wrong answer costs nothing. A search box where the reader can see the chunks themselves already has the habit built in: the person reading is the judge.
  • The question is cheap and the wait is not. Eight calls in a row is eight waits in a row.

Reach for the judges when the answer goes somewhere a person acts on it without reading the chunks, when questions arrive that the corpus was never meant to cover, and when nobody is at the terminal to keep the habit by hand.

Three ways this goes wrong

From the outside all three look the same: the answer was wrong, and the judges let it through, or the run never ended.

  • A judge that always says yes — its instruction is too loose to refuse anything, so every chunk is relevant and every answer is grounded, and the graph is the plain chain with eight calls.
  • A judge that always says no — its instruction is too hard, so the backwards edge is taken every time and only the count ends the run.
  • A fallback that floods — the web result is long and joins the documents unjudged, so the answer is grounded in it and the handbook chunk is lost in the crowd.

Telling them apart takes one habit, and it is the LangSmith Module's habit brought forward: test each judge on its own, with one input it must say yes to and one it must say no to, before wiring it into the graph. A relevance judge handed the car chunk and the question "how do I make pizza" has to say no. One that says yes is the first failure, and it is found in a test that takes a second, not in a run that took eight calls.

What this leaves for later

Named here, and needed by nothing above.

  • A dataset for the judges — the two-input test above, kept as rows and run on every change, which is what the LangSmith Module's datasets are for.
  • Keeping private text on the machine — when the documents are a contract and the fallback is a web search, the question has to be rewritten without the names and amounts before it leaves. A node for that sits between judge documents and web search, and this page does not build it.

The short version

  • A judge is one model call, given two things and asked one yes-or-no question, answering in a bool.
  • The three RAG failures get three judges: relevance on each chunk, grounding on the answer against the chunks, usefulness on the answer against the question.
  • The judges sit on the edges: irrelevant chunks are dropped and send the run to the web, an ungrounded answer goes back to generate, a useless one goes out to search.
  • The two backwards edges end when a judge says yes, and a count in the state ends them when it never does.
  • The cost is real, one call became eight, so test each judge alone first, and keep the plain chain where a wrong answer costs nothing.

One call, or six

Say you want the text out of a file. In C# you can write this:

var text = File.ReadAllText(path);

One line. You did not pick a read buffer size. You did not work out whether the file is UTF-8. You did not open a handle and remember to close it. Somebody wrote all of that once, and put it behind a door with one handle on it.

Now picture the other version. Open the file. Ask what encoding it uses. Pick a buffer size. Read chunk by chunk. Close the handle. Cope with closing failing. Same result. Six decisions you now own, in every place you read a file.

This Module is about the difference between those two, and how to end up with the first one on purpose.

The trade every code module makes

A code module is any piece of code you can call from outside: a class, a file, a package. Kata also uses the word Module for a page like this one, so where both meanings are in play this page says code module.

Every code module has two sides.

  • Its surface is everything a caller must know to use it: method names, parameters, configuration values, the order calls have to happen in, and what it throws. A caller is any code that uses it.
  • Its functionality is everything it does for that caller.

The surface is the cost. Every caller pays it once to learn it, and pays again each time it changes. The functionality is the benefit. So the goal has a shape: hide as much work as possible behind as small a surface as possible.

File.ReadAllText(path) is a deep code module. One thing to learn, and buffering, encoding, handle lifetime, and platform differences all stay somebody else's problem.

A wrapper class whose five methods each forward to one call underneath is a shallow one. Its surface is nearly as large as its insides. It adds something to learn without removing anything to know.

Depth is a ratio you can eyeball: how much does this hide, per thing a caller must learn?

Information hiding

Suppose your app saves notes to disk as JSON files, one per note, in a folder under the user's home directory. That choice — JSON, one file each, that folder — is a design decision: a choice somebody had to make, that could have gone another way.

Information hiding means each code module owns a few such decisions and keeps them to itself. Hidden has a hard test. A decision is hidden when no caller could tell if it changed.

So try it. Swap the JSON files for a SQLite database. If any caller has to be edited, the storage decision was never hidden. It had leaked out into the callers, one piece at a time.

Leakage has three countable tells

You do not need taste to spot leakage. You can count it.

  1. Pass-through values. A pass-through is an argument a caller takes and never uses itself — it only hands it onward. If SaveNote accepts a folder path so it can give that path to the writer underneath, the folder decision is living in the caller. Count them.
  2. Required call order. Open, then Read, then Close. The module's own lifecycle has become a ritual the caller performs. Splitting code up this way has a name: temporal decomposition, dividing by when things happen instead of by what stays hidden. It reads naturally, and it leaks.
  3. Duplicated knowledge. The same format string, magic path, or constant appears inside the module and in the code that calls it. Grep for it. Two copies means two places to edit the day the decision changes.

Making a code module deeper

  • Defaults over knobs. Every parameter is surface. Send(message), with a sensible retry policy chosen inside, beats Send(message, retries, backoffMs, timeout). Pick a good default and the question stops being asked.
  • Somewhat general-purpose. Save(name, text) outlives SaveQuarterlyReportAsCsv(...). The general shape usually has the smaller surface, and it survives the next feature request.
  • Pull complexity downward. Better that one module is a little harder to write than that twenty callers are each a little harder to write. The author of the module pays once. Every caller pays forever.

Why this idea comes first

Most named design principles fall out of one question: what does this code module hide, and from whom? Single responsibility and dependency inversion are both answers to it. Read the other Modules in whatever order you like — this question sits under all of them.

Three files break, and none of them was the one you edited

A team keeps orders in a database table. The pricing code reads that table directly. So does the code that formats the confirmation email. So does the test setup. One morning a column called total is renamed total_amount. Three files break, and none of them was the file anyone meant to change.

Nobody was careless. It is the mechanical result of many pieces of code knowing one detail. This Module is about noticing which pieces know what, and choosing that on purpose.

Every dependency is an arrow

If your code names something else — constructs it, calls it, or mentions its type in a signature — it depends on that thing. Draw it as an arrow pointing from your code at what it names.

An arrow is a bet: this will not change under me. When A points at B, every change to B can force a change to A. Chain a few arrows and one edit ripples, exactly as the renamed column did.

You cannot remove the arrows. Code that depends on nothing does nothing. What you choose is where they point.

  • Something stable changes rarely. Usually it is a small abstraction that says what is needed: "something that can save an order", "something that tells the time".
  • Something volatile changes often. Usually it is a concrete detail of how: a particular database, a file format, a vendor SDK, this quarter's discount rule.

Aim your arrows at the stable things. Then make the volatile details point at those same stable things from their side. Now the details can churn and nothing upstream notices.

Coupling and cohesion — both countable

Coupling is how much one piece of code must know about another to use it. Count it. How many of B's types appear in A's fields, signatures, and method bodies? If B's constructor gained a parameter, how many files would stop compiling? A high count means A depends on B's shape, not only on the service B performs.

Cohesion is whether the things inside one class belong together. Test it without taste: state the class's responsibility in one sentence. If the sentence needs the word "and", the class is holding two responsibilities — and everything depending on it inherits both reasons to change. That is single responsibility, the S in SOLID (a five-letter reminder of five design guidelines), measured by doing rather than by opinion.

High cohesion keeps each arrow's target small and single-purpose. Low coupling keeps the number of arrows into any volatile thing near zero.

Reversing an arrow

Concrete case first. A RenewalService decides when a subscription renews. Written the obvious way, it creates a SqlSubscriptionRepository itself. The renewal rules now point straight at SQL Server.

Turn that arrow around in three moves.

  1. The policy — the code carrying the business decision, here the renewal rules — declares a small C# interface describing only what it needs, named in its own vocabulary: ISubscriptions, with Find and Save.
  2. The volatile detail — the SQL repository — implements that interface. The arrow now runs from the detail to the abstraction, the reverse of where it started. That reversal is the whole of dependency inversion, the D in SOLID.
  3. The outermost edge of the program — the startup code that wires the pieces together — picks the concrete class and hands it in through the constructor.

Watch what this does to change. Swapping SQL Server for Postgres means writing one new class and editing one line at the edge. The renewal rules are untouched. If you cannot make that claim about your own code — if swapping a detail would edit the policy — an arrow is pointing the wrong way.

SOLID's other letters need no theory of their own here. Open/closed, substitutability, and narrow C# interfaces turn up in this Module's Self-Check as things you count or do.

Five checks, each yes or no

  • Does a new for a volatile class — database, file system, HTTP client, clock — appear inside business logic? Every new is an arrow hard-wired at one concrete type.
  • Do the using directives at the top of your core logic name infrastructure: data access, network, vendor SDKs? Each one is a path a ripple can travel along.
  • Pretend one detail changed: the storage technology, the message format. Count the files you would edit. More than the implementation itself plus one line of startup wiring means the arrows point at the detail.
  • Can the Test Suite at the Target Interface — the tests committed with an Exercise, written against the fixed outer edge it hands you — run with no real database and no network? If not, the policy depends on the detail.
  • State each class's responsibility in one sentence. Any "and" is low cohesion, and every dependent inherits both halves.

The Exercises in this Module plant exactly these flaws — a Smell is a flaw planted on purpose for you to find. One is policy code that constructs its own details; one is business rules threaded through a concrete storage format. Your job is to turn the arrows around, and the Target Interface shows where they have to end up pointing.

Two tests for the same behavior

A class called Cart works out an order total. Somebody writes two tests for it.

The first calls cart.Total() and checks the number that comes back. The second reaches inside and checks that a private helper named ApplyLineDiscount ran twice.

Next week the inside of Cart is rewritten. Every total is identical. The first test still passes. The second goes red, because the helper it named no longer exists.

Nothing a user could notice changed, and yet a test failed. The second test was pointed at the wrong thing. This Module is about where to point a test so it stays useful.

Tests belong at the boundary

A boundary is the outside edge of a piece of code: the small set of calls other code is allowed to make. In Kata's Exercises that edge has a name — the Target Interface, the signatures an Exercise fixes in advance and you may not change. Everything behind it is yours.

Write tests at that edge and nowhere else. A test at the boundary says what the code must do for its caller. A test against an internal class says how the code happens to do it today.

A test earns its keep two ways: it fails when the behavior is wrong, and it stays green when the behavior is preserved. Tests bound to internals fail both duties.

  • They can pass while the visible behavior is broken, because they watched a helper instead of the outcome.
  • They fail during a rewrite that changed nothing a caller could notice.

When the second happens you either abandon the rewrite or rewrite the tests. A rewritten test proves little. It was written to match the new code, not to constrain it.

Boundary tests give you the opposite deal. Rename, split, merge, or delete anything behind the Target Interface. If the tests stay green, the behavior survived. That is what makes an Exercise's Test Suite — the tests committed with it, which you run yourself in your own IDE — the trustworthy part of the material. It does not care how you got there.

Two countable signs your tests sit too deep:

  • Read the using directives and constructor calls in the test file. Count the types a real caller of the Target Interface would never touch. Each one is a test reaching inside.
  • Rename a private method or an internal class, changing no behavior. Count the tests that fail or stop compiling. Each one was bound to structure.

Hidden dependencies show up at the boundary

Some things a class reaches for are outside its control: the system clock, the file system, the network. Call those volatile dependencies. Grabbing one directly makes tests awkward, and the awkwardness is the signal.

Concrete case. A method says a token expires "in 14 days", and it reads DateTime.UtcNow inside itself to work that out. A test cannot know the exact moment the method ran, so it re-does the arithmetic and allows a few seconds of slack. The test is now vague, and one day it fails for no reason at all.

The fix comes in through the boundary, and it is the move the Dependency Direction Module makes, seen from the testing side. Let the clock arrive as a small C# interface the caller supplies — an IClock with one UtcNow — and have the Test Suite hand in a fake clock it fully controls. Now the exact moment is a plain assertion: the last legal second still works, the first expired second does not. The same move works for a store, an HTTP client, or a random number.

The TDD loop, and small steps as the speed limit

TDD is short for test-driven development: write the failing test first, then the code that satisfies it. Three moves, repeated.

  1. Red. Write one failing test against the Target Interface. Run it and read the failure. It has to fail because the behavior is missing, not because of a typo or a broken setup.
  2. Green. Write the least code that makes it pass. Not the best code. Not the general solution. The least.
  3. Refactor. With every test green, improve whatever you like behind the boundary. Refactoring means changing the shape of the code without changing what it does. Tests do not change in this step. Wanting to edit one here means either the test was written against internals, or the behavior is changing under the refactor's name.

Small steps are not a style preference. They are the speed limit that keeps the loop informative. One test per loop. After each Green, say in one sentence what a caller can now rely on that they could not before — a sentence needing "and" was two steps.

Keep each change small enough that when the suite goes red you know which edit did it without opening a debugger. The failure locates itself. Having to bisect your own last ten minutes of work means the steps were too big.

How this runs in your Exercises

  • A construct-type Exercise starts from a stub. Run dotnet test before writing anything and count the failures. That number is your worklist. Make one test pass at a time, in the order that needs the least code, and build nothing no red test demands.
  • A refactor-type Exercise starts green, and stays green after every small step.
  • Either way, finish with one check: could someone rebuild the implementation from the Target Interface and the Test Suite alone? If yes, your tests describe behavior.

The Exercises here plant exactly these flaws — a Smell is a flaw planted on purpose for you to find. One widens a surface so tests can watch the internals run; one reads a clock in place instead of taking it in. The Self-Check asks the same countable questions, and they are the questions to ask of any code you and an AI write together from now on.

The same thing, called three things

A lending codebase has a class called Record, a database row the team calls an Entry, and a LoanDto that crosses one boundary. All three are the same idea: a loan. Nobody wrote that down. Every reader works it out again, and holds a little translation table in their head while they read.

Nothing is broken. No test fails. It costs a few minutes per reader, forever, and it makes search unreliable: looking for "loan" finds a third of the places loans are handled.

This Module is about paying that cost once instead of on every reading.

The cheapest change with the highest leverage

Renaming is the cheapest change you can make to a codebase. No behavior moves. When the tests sit at the Target Interface — the fixed outer edge of the code, which names on the inside cannot affect — nothing breaks.

It is also the highest-leverage change, because a name is read hundreds of times for every once it is written: by you, by the next reader, and by every AI tool you work with. A model prompted in the domain's own words writes code you do not have to translate back. A model prompted over Managers and ProcessDatas guesses.

One concept, one name — everywhere

A domain is the subject your program is about: lending, ticketing, payroll. A Ubiquitous Language is one agreed list of words for the things in that domain, used everywhere — in conversation, in documents, in commit messages, and in code.

The rule has two halves. One concept gets exactly one name. One name means exactly one concept. When the domain says loan, the code says Loan — not Record in one file and Entry in another. When a concept has no name yet, name it first, then write the code.

The payoff is mechanical, not a matter of taste.

  • Search for a domain word and you find every place the code touches that concept. Grep becomes a design tool.
  • A sentence spoken by someone who knows the business turns into code almost word for word, and back again.
  • A new reader predicts what a method does from its signature alone, before opening the body.

Four checks that need no taste

A good name states what the reader would otherwise have to discover by reading the implementation. A bad name forces that reading — or lies, so the reader trusts it and is wrong. Four ways to tell them apart with nobody's opinion involved:

  1. The prediction check. Read only the name and the signature, and write down what you expect the member to do. Then read the body. Anything the body did that your prediction missed — or promised and skipped — is a naming defect, whichever direction it runs.
  2. The synonym count. Pick one domain concept and search for every word the code uses for it. A count above one means every reader carries the translation table from the top of this page.
  3. The vague-word grep. Search for Manager, Helper, Util, Handler, Process, Data, Info, temp, flag, and item. Each hit announces that a thing exists without saying what it is or does. Ask of each one: which noun or verb from this member's one-sentence job is missing from its name?
  4. The scope-honesty check. A side effect is anything a call changes besides producing its answer. Count the side effects the name does not mention — a Get that creates a row, a Validate that saves. Any count above zero is a lie the codebase tells hundreds of times.

A name that will not come is a design probe

Naming is not decoration applied after the design. It is the cheapest design review you can run.

When a class cannot be named without and, or, or a vague word, it usually holds more than one responsibility, and the missing name is telling you where to split it. State each class's responsibility in one sentence beginning with its name: a sentence that needs "and" was two classes.

When two parts of a system use different words for the same concept, the line between them forces every caller to translate. That line is a seam — a place where a system naturally comes apart, and so a place where a boundary can be drawn cleanly. A clash of vocabulary marks a seam that needs one owner and one word.

How this runs in your Exercises

  • In the refactor-type Exercise the behavior is already correct and the Test Suite starts green. The flaw planted for you to find — the Smell — is entirely in the names. The Target Interface's names are the Ubiquitous Language; rename everything behind it into that language, keeping the suite green after each step.
  • In the construct-type Exercise the temptation is to let implementation vocabulary write the code: dict, entry, flag, a helper called Manager. The folder's glossary is the domain's language, and every name you introduce comes from it.
  • Either way, finish with the four checks above. The Self-Check asks the same countable questions, and they are the questions to ask of every piece of code you and an AI write together from now on.

A delete that throws

Call File.Delete(path) on a file that is not there. What should happen?

One design throws an exception. Every caller that deletes a file now writes a try/catch, or checks first, or both. Twenty callers, twenty small rituals, and each ritual is code nobody tests.

The other design says this method means "make sure the file is gone". The file is already gone, so the work is done, so the method returns. No exception, no catch, nothing for the caller to remember.

Both designs are correct. Only one of them is cheap. This Module is about choosing the second on purpose.

Errors are part of the surface

A method's surface is everything a caller must know to use it: its parameters, what it returns, and every way it can fail. Exceptions are part of that. The happy path is written once. The error paths are re-written in every caller, forever, and they are the least-tested code in most systems.

You can count the cost. Pick a method, list what it can throw, and count the catch blocks that exist across the codebase because of it. That number is the price of its error design.

The move that drives the number down is to define errors out of existence — not swallowing failures, but shrinking the set of conditions that count as failures at all.

The four moves, in order of preference

  1. Define the error out of existence. Redefine the operation so the edge case is ordinary behavior. Deleting a missing file means "ensure it is gone", which succeeds either way. Reading past the end of a range returns the overlapping part, possibly empty, never a throw. Ask of every throw: what would this method promise if this case were allowed?
  2. Mask the error inside the module. To mask an error is to deal with the condition where the knowledge to deal with it lives. Retry the flaky network call inside the client class, not in every caller. The error still happens; it stops being anybody else's problem. This is error design's version of a deep module — one that hides a lot of work behind a small surface: the complexity is absorbed behind the Target Interface instead of pushed through it.
  3. Aggregate the handling. When errors must travel outward, aggregate them: catch them at a single outer edge — one handler that turns failures into responses — instead of scattering try/catch through every controller and service. Ten handlers doing the same thing are nine too many.
  4. Crash. Some conditions mean the program has a bug: corrupted state, or a broken invariant — a statement meant to be true at all times, such as "an order always has at least one line". The right handling is often none. Fail loudly at the fault instead of limping on to fail somewhere confusing.

What this looks like in backend .NET

  • Exceptions are for the exceptional. When a caller is expected to decide what to do next — "not found", "already taken", "out of stock" — that outcome belongs in the return type: a bool, a TryGet method, a small result object. There the compiler makes the caller face it. A catch used as an if is control flow in a costume.
  • What a method throws is a design decision. A method that lets SqlException, HttpRequestException, and JsonException escape has a promise that names three infrastructure technologies. Its callers now depend on choices made inside it. Mask those errors, or translate them into one type that speaks the caller's language.
  • Special values are errors in disguise. Returning null where the caller will use the result immediately, or -1 where the caller will use it as an index, moves the crash away from its cause without removing it. Defining the error out of existence means what comes back is usable as it stands: an empty collection you can loop over, a no-op you can ignore.
  • Not every failure can be designed away. The database will go down. Expected outcomes belong in the return type. Genuine failures travel to one handler. Impossible states crash. What must not survive is the mush in between: routine conditions thrown as exceptions and caught piecemeal at every call site.

Three checks that need no taste

  1. The escape count. For each public method, count the distinct exception types it can let out. Every type above zero is a catalog entry every caller inherits.
  2. The happy-path catch. Find every catch the code relies on to produce a normal result. Each one is an expected outcome dressed as an exception — the costume check above, run mechanically.
  3. The unless test. Write each method's promise in one sentence, error cases included. A sentence needing "unless" or "except" more than once is pointing at a rewording that would define the error out of existence, and the rewording is usually the redesign.

How this runs in your Exercises

  • In the refactor-type Exercise the Target Interface — the fixed signatures you must end up behind — already defines every expected condition as an ordinary result. The code behind it still raises and catches its own exceptions for those same conditions, in every method. That is the flaw planted for you to find, the Smell.
